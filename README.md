


### Задание 1

#### Выбор решения для микрофронтендов

Я выбрал **Module Federation**.
- Проект на React, в проекте уже используется вебпак - думаю это решение подходит исходя из опыта команды
- Будет относительно просто мигрировать
- Подходит для структуры зависимости приложения (есть общие зависимости между микрофронтендами, можно это использовать для оптимизации банда)
- Позволяет динамически подключать модули без перезагрузки страницы
- Поддерживает независимый деплой

#### Разделение на микрофронтенды

Буду использовать подход вертикальной нарезки. Для общения между фронтонами я бы предложил использовать решение для работы с глобальным стертом (Redux, Mobx или нативную систему контекстов React). Пример где это будет полезно - CurrentUserContext.

В проекте будет 4 приложения - 3 микрофронтенда по функциональным зонам ответственности и приложение-контейнер

#### container-app
Зона ответственности - роутинг, подгрузка модулей, отображение хедера и футера

- `Header`
- `Footer`
- `ProtectedRoute`
- `CurrentUserContext`

#### auth-app
Зона ответственности - аутентификация, авторизация, хранение и обновление связанного с этим состояния

- `Login` & `Register`
- Логика работы с API авторизации

#### profile-app
Зона ответственности - данные профиля пользователя, имя, картинка профиля и т.п. Отображение и редактирование
- `EditAvatarPopup`
- `EditProfilePopup`
  
#### gallery-app
Зона ответственности - работа с карточками и изображениями. Просмотр и добавление карточек, лайки


#### Общие компоненты

Повторно используемые элементы, такие как `PopupWithForm`, выносятся в отдельный модуль `shared`, не взаимодействующий напрямую с глобальным состоянием.

#### Дальнейшие шаги

Потребуется частичный рефакторинг API: разделение логики на подмодули (auth, profile, gallery). Также предполагается отделить логику рендера и состояния в соответствующие микрофронты.

### Задание 2

Я разделил монолит на 6 сервисов по зонам ответственности:

- Сервис пользователей (Users)
- Сервис платежей (Payments)
- Сервис поддержки и апелляций (Support)
- Сервис аукционов (Auctions)
- Сервис товаров и услуг (Catalog)
- Сервис заказов (Orders)

Зоны ответственности обозначены функциями, относящимися к каждому из сервисов. Взаимодействия основываются на шине событий Kafka.
